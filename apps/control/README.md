# Managed control boundary

Tasks 7/8 supply authenticated registry, administration, edit admission/reconciliation, private artifact storage and durable generation workers. Generation is advertised only when the real queue and storage are configured. Validated generation archives its output and waits at a durable publication reservation. External publication and export remain **unavailable** pending their production adapters. No demo worker/model/publication adapter is imported by control. The native local mode remains separate. Its main WebView CSP permits HTTPS connections for the configured Auth/API endpoints while retaining local-only scripts, no frames and no objects. A main-local-only native command validates the scoped HTTPS preview URL and uses the OS browser opener without a shell. Native execution/GUI behavior still requires supported-platform acceptance; tests disable the launcher.

Run all numbered migrations in order as the database migration owner in a Supabase project with `auth.users`, `auth.uid()`, `authenticated` and `anon` (including `002_invitation_attempts.sql` and `003_queue_leases.sql`). The application uses a server-only PostgreSQL connection/pool. The client roles receive SELECT-only RLS-protected registry/chat data; private tables and artifact keys are never client-readable. The direct SQL application credential is a deployment secret. Do not put it in Vite configuration.

Deploy the control workspace with its `api/index.ts` default `{fetch}` Web Standard export and `vercel.json` rewrite to `/api/index`, preserving imports from the monorepo. Set server environment `DATABASE_URL`, `SUPABASE_URL`, `CONTROL_PUBLIC_ORIGIN` (HTTPS origin only), and comma-separated `CONTROL_ALLOWED_ORIGINS` for the trusted desktop/browser origins. Configure the actual desktop origin on the target platform. Optional server R2 configuration is `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`; optional `PREVIEW_SIGNING_KEY` is a separate random base64-encoded key of at least 32 bytes. None are returned by `/session` or `/admin/integrations`. Disable all public R2 bucket/custom-domain access. Use asymmetric Supabase RS256/ES256 signing keys; legacy HS256 is deliberately rejected by this verifier.

Provision the initial Auth account explicitly using the deployment administrator. After migration and `npm run build`, run `node scripts/bootstrap-managed.mjs <verified-auth-user-uuid>` with the server-only environment and `SUPABASE_SERVICE_ROLE_KEY`. This verifies that exact Auth subject, creates the first administrator and seeds the catalogue. It is never an HTTP signup path.

For later admin invitations, set the project's **server-only service_role API key** as `SUPABASE_SERVICE_ROLE_KEY` on the control deployment. The entry wires the concrete Supabase Admin adapter only when this is present; otherwise invitations remain unavailable. `SUPABASE_URL` must be an HTTPS origin without credentials/path/query/fragment. The key is used only in headers to that fixed origin with redirects disabled, never in client configuration or error messages. An installation using new secret-key conventions must supply a supported service_role credential for this adapter; do not substitute a publishable key. No invitation emails were sent in local tests.

Before using invitations, configure Supabase Auth's **Invite user** email template to display the code instead of a confirmation link, for example:

```html
<h2>Site Factory invitation</h2>
<p>Open Site Factory → Режим работы → Принять приглашение по коду.</p>
<p>Use this email address and code: <strong>{{ .Token }}</strong></p>
<p>Then choose a password. Your administrator supplies the API origin, Supabase origin and publishable key separately.</p>
```

Configure the deployment's SMTP/email delivery and OTP lifetime in Supabase. Do not put credentials, user tokens or control capabilities in the template. The desktop uses `verifyOtp({email,token,type:'invite'})`, then `updateUser({password})`; it needs no callback URL/deep link and exposes no public signup. The code clears immediately. A rejected password keeps the verified session in memory for a direct password retry. After password setup, a recipient awaiting membership sees instructions to ask the administrator to repeat the same email/role invitation and then sign in with the password. Switching to local remains explicit.

Invitation operations have a unique durable email/role intent plus a private send-attempt record. Fresh admin authorization is checked in short write transactions, and no HTTP request runs inside a SQL transaction. The provider lists users using supported `page`/`per_page` pagination (100 per page, bounded at 1000 pages) and rechecks the exact email/ID using privileged Admin GET. An existing confirmed identity needs no new email. A successful invite response is durably bound to its operation before membership completion; retries verify that ID. A lost/error response never triggers automatic resend or membership from `user_metadata`/`invited_at`. An explicit admin retry may recover an independently verified, exact-email **confirmed** identity. Unknown/unconfirmed outcomes remain pending with a safe error; if no code was delivered or it expired, an operator must investigate the provider and resolve the account through the deployment's Auth administration. The application does not silently reset the attempt or resend mail. Provider failures and malformed/mismatched identity responses never grant access. Existing memberships are not promoted/reactivated by invitation retries.

Desktop “Режим работы” takes an HTTPS API origin, the project's Supabase URL and **publishable** key. Tokens are held in the Auth client's memory, refreshed by that client, and sent as Authorization headers. Password fields clear on submission. Remote failures stay remote; switching to local requires an explicit user action. The API resolves the active membership on every request and again under write transactions. Role claims/user_metadata have no authority. Admin controls are also checked on the server.

Control JSON is limited to 64 KB. Node resource uploads use `/uploads/prepare`, direct signed R2 PUTs, then `/uploads/complete`; private state is a separate resource, never base64 in control JSON. PUT capabilities expire in 600 seconds and sign Content-Type plus If-None-Match `*`. URLs themselves remain reusable until expiry; conditional create and never-reused keys provide immutable writes. Revocation cannot recall an issued URL, but subsequent completion is fenced. HEAD is not digest proof: the server verifies actual bytes and both digests before creating consumable immutable metadata, and verifies again on read. Checkpoint state/files use `private/checkpoints/`; public site artifacts use `private/artifacts/`.

Preview grants bind user/site/immutable revision, last ten minutes, and require fresh membership even after minting. The scoped capability is exchanged for an HttpOnly path-scoped cookie and redirected to a clean URL; it is neither a user access token nor a Vercel/master bypass secret. HTML is sandboxed and cannot connect to external services. Only authorized revision artifact files are served. No checkpoint route exists for users. A separate parse-aware HTML/CSS/srcset projection rewrites static relative and root-relative resources to exact-path asset capabilities; no archived bytes are changed. Each asset capability expires with its parent grant and rechecks membership/site/revision/path. This keeps sandboxed assets working with third-party cookies blocked. The initial top-level cookie is SameSite=None; Secure; HttpOnly and only authorizes read-only revision paths. The preview remains an opaque origin; scripts cannot connect to APIs. Dynamic URLs constructed by JavaScript and dependent resource links inside standalone SVG or advanced unsupported CSS forms are not rewritten; their preview behavior is not claimed. No external resource is fetched or proxied.

## Task 8 contracts

`LeaseAuthority.assertCurrent(tx,workerId,lease)` is transaction-scoped and has **no default production implementation**. It must check fresh revocation, running job, exact worker/generation, unexpired stored lease and current site admission. Ignore request expiresAt. Lock order: site row, worker row, job row, site_operations; sample `clock_timestamp()` after locks. Revocation must hold worker locks; later cancellation/reclaim and fenced site CAS must use compatible order. No object/model/provider work occurs inside SQL transactions.

Controller admission is a bounded 120-second database record. Every write/CAS checks its exact token and server-time expiry. Candidate/job creation transfers admission to the queued job atomically; the following shared-domain enqueue is idempotent. Finally-release removes only its own controller admission. Active jobs block competing edits. Completed/cancelled/needs_attention jobs whose worker ownership ended allow reconciliation/rejection. Task 8 must serialize explicit retry with that same admission rule. Read polling while busy projects durable records and actual job status; idle authorized editing polling reuses the existing core reconciliation/evidence logic.

Upload prepare persists immutable IDs/keys and expectedCheckpointId. Completion rechecks authority and predecessor and creates an **unreferenced** immutable checkpoint; it never advances job progress. Task 8 must atomically commit `job.checkpoint_id`, stage and the matching JSON Job projection with expected predecessor and current authority. Exact commit replay is idempotent; a different delayed predecessor cannot replace newer progress. Older-generation committed checkpoints remain readable to a new owner through a future authorized worker resource route. Add a worker fenced site-CAS entry point; the ordinary repository CAS accepts only a live controller admission and cannot authorize a worker. Private continuation/configuration/recovery tickets remain private.

## Managed devices and durable queue

In the native application, sign in as an administrator to the configured HTTPS control origin, open **Исполнители**, configure a real model, register this device, and explicitly start it. Stop releases cooperative work; remote Pause finishes the current stage before releasing it. Resume requeues this device's paused jobs without erasing checkpoints. Cancel invalidates a job generation and preserves published content. Revocation invalidates the machine credential independently of the administrator session. No online devices means jobs remain queued.

Enrollment is a dedicated main-local native command, not generic renderer dispatch. The fixed sidecar generates a UUID and 32 random bytes (canonical 43-character base64url token). Rust atomically stores the pending descriptor and credential together in the OS secret store before HTTP. The transient administrator access token is never stored. `POST /workers/enroll` takes `{workerId,name,token,controlOrigin}` under a freshly checked administrator bearer and returns only `{workerId,name}`. The server stores only token hash, identity and immutable enrolling-admin/name/origin binding. Exact retries reuse that identity and credential; a different binding conflicts, and revoked identities never revive. A lost HTTP response or ambiguous OS-store write must be retried using the saved pending identity. Rotation is explicit revoke followed by a new enrollment. An existing saved identity is not silently overwritten. Native status returns only safe summary fields. Start, stop and revoke require the renderer's configured expectedOrigin; native code compares it with the saved enrollment before any private sidecar action or bearer forwarding and preserves the saved credential on mismatch. Requests use fixed paths at the configured HTTPS origin and reject redirects.

Claims use `FOR UPDATE SKIP LOCKED`, server time after locks, a 120000 ms lease and at most two live jobs per device. Worker identity comes from fresh token lookup. Every protected mutation checks exact generation, unexpired stored lease and matching site admission in its write transaction. Heartbeat interval is 30000 ms. Upload completion produces immutable unreferenced metadata; only checkpoint CAS with its expected predecessor advances the durable stage. A new owner may read the last committed older-generation snapshot, while the old owner cannot commit. All provider/storage/browser work runs outside SQL transactions.

Worker HTTP uses `POST /worker/jobs/claim` and lease-bound `heartbeat`, `checkpoint`, `finish`, `pause-status`, `pause-boundary`, `site`, `revision`, `catalog`, `snapshot`, `resource`, `artifact`, and `publication` actions under `/worker/jobs/:id/`. User retry/cancel routes are `/sites/:id/jobs/retry|cancel`. Their write transaction checks the locked job kind and fresh membership: editing requires scoped site:edit; generation requires the site owner or an administrator, not assigned read access alone. Classified account/configuration recovery requires an explicit request and exact private checkpoint ticket; retry counters, files and known usage remain intact. Unknown-response retries persist optional `uncertainRequests` separately from known token totals. This is a count of prior attempts with unknown token/billing usage, never estimated charges.

Publication reservation binds immutable request key, manifest/revision/base/checkpoint and originating job or controller. Atomic handoff changes site admission to publication; cancel, expiry or revocation cannot remove that exclusion. Task 9 must verify provider evidence and install the matching revision/pointer in the server settlement transaction. There is no worker HTTP settlement or worker authority to assert provider success. Task 9 must integrate server-settlement acknowledgment into `runJob`, including an exact settlement made while a device was offline; merely changing the remote publication result from pending to published would incorrectly invoke currently forbidden worker revision/pointer writes.
