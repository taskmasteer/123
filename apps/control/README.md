# Managed control boundary

Tasks 7–9 supply authenticated registry, administration, edit admission/reconciliation, private artifact storage, durable generation workers and resumable Vercel publication. Generation is advertised only when the real queue and storage are configured. Publication additionally requires the server configuration below. Administrators can read/download original source and create independent recovery snapshots. No demo worker/model/publication adapter is imported by control. The native local mode remains separate. Its main WebView CSP permits HTTPS connections for the configured Auth/API endpoints while retaining local-only scripts, no frames and no objects. A main-local-only native command validates the scoped HTTPS preview URL and uses the OS browser opener without a shell. Native execution/GUI behavior still requires supported-platform acceptance; tests disable the launcher.

Run all numbered migrations in order as the database migration owner in a Supabase project with `auth.users`, `auth.uid()`, `authenticated` and `anon` (including `002_invitation_attempts.sql`, `003_queue_leases.sql`, `004_publication_intents.sql` and `005_publication_attachment_retry.sql`). The application uses a server-only PostgreSQL connection/pool. The client roles receive SELECT-only RLS-protected registry/chat data; private tables and artifact keys are never client-readable. The direct SQL application credential is a deployment secret. Do not put it in Vite configuration.

Deploy the control workspace with its `api/index.ts` default `{fetch}` Web Standard export and `vercel.json` rewrite to `/api/index`, preserving imports from the monorepo. Set server environment `DATABASE_URL`, `SUPABASE_URL`, `CONTROL_PUBLIC_ORIGIN` (HTTPS origin only), and comma-separated `CONTROL_ALLOWED_ORIGINS` for the trusted desktop/browser origins. Configure the actual desktop origin on the target platform. Optional server R2 configuration is `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`; optional `PREVIEW_SIGNING_KEY` is a separate random base64-encoded key of at least 32 bytes. None are returned by `/session` or `/admin/integrations`. Disable all public R2 bucket/custom-domain access. Use asymmetric Supabase RS256/ES256 signing keys; legacy HS256 is deliberately rejected by this verifier.

Provision the initial Auth account explicitly using the deployment administrator. After migration and `npm run build`, run `node scripts/bootstrap-managed.mjs <verified-auth-user-uuid>` with the server-only environment and `SUPABASE_SERVICE_ROLE_KEY`. This verifies that exact Auth subject, creates the first administrator and seeds the catalogue. It is never an HTTP signup path.

For later admin invitations, set the project's **server-only service_role API key** as `SUPABASE_SERVICE_ROLE_KEY` on the control deployment. The entry wires the concrete Supabase Admin adapter only when this is present; otherwise invitations remain unavailable. `SUPABASE_URL` must be an HTTPS origin without credentials/path/query/fragment. The key is used only in headers to that fixed origin with redirects disabled, never in client configuration or error messages. An installation using new secret-key conventions must supply a supported service_role credential for this adapter; do not substitute a publishable key. No invitation emails were sent in local tests.

Before using invitations, configure Supabase Auth's **Invite user** email template to display the code instead of a confirmation link, for example:

```html
<h2>Site Factory invitation</h2>
<p>Open Site Factory → Режим работы → Принять приглашение по коду.</p>
<p>Use this email address and code: <strong>{{ .Token }}</strong></p>
<p>Then choose a password. Your administrator supplies the API origin, Supabase origin and publishable key separately.</p>
```

Configure the deployment's SMTP/email delivery and OTP lifetime in Supabase. Do not put credentials, user tokens or control capabilities in the template. The desktop uses `verifyOtp({email,token,type:'invite'})`, then `updateUser({password})`; it needs no callback URL/deep link and exposes no public signup. The code clears immediately. A rejected password keeps the verified session in memory for a direct password retry. After password setup, a recipient awaiting membership sees instructions to ask the administrator to repeat the same email/role invitation and then sign in with the password. Switching to local remains explicit.

Invitation operations have a unique durable email/role intent plus a private send-attempt record. Fresh admin authorization is checked in short write transactions, and no HTTP request runs inside a SQL transaction. The provider lists users using supported `page`/`per_page` pagination (100 per page, bounded at 1000 pages) and rechecks the exact email/ID using privileged Admin GET. An existing confirmed identity needs no new email. A successful invite response is durably bound to its operation before membership completion; retries verify that ID. A lost/error response never triggers automatic resend or membership from `user_metadata`/`invited_at`. An explicit admin retry may recover an independently verified, exact-email **confirmed** identity. Unknown/unconfirmed outcomes remain pending with a safe error; if no code was delivered or it expired, an operator must investigate the provider and resolve the account through the deployment's Auth administration. The application does not silently reset the attempt or resend mail. Provider failures and malformed/mismatched identity responses never grant access. Existing memberships are not promoted/reactivated by invitation retries.

Desktop “Режим работы” takes an HTTPS API origin, the project's Supabase URL and **publishable** key. Tokens are held in the Auth client's memory, refreshed by that client, and sent as Authorization headers. Password fields clear on submission. Remote failures stay remote; switching to local requires an explicit user action. The API resolves the active membership on every request and again under write transactions. Role claims/user_metadata have no authority. Admin controls are also checked on the server.

Control JSON is limited to 64 KB. Node resource uploads use `/uploads/prepare`, direct signed R2 PUTs, then `/uploads/complete`; private state is a separate resource, never base64 in control JSON. PUT capabilities expire in 600 seconds and sign Content-Type plus If-None-Match `*`. URLs themselves remain reusable until expiry; conditional create and never-reused keys provide immutable writes. Revocation cannot recall an issued URL, but subsequent completion is fenced. HEAD is not digest proof: the server verifies actual bytes and both digests before creating consumable immutable metadata, and verifies again on read. Checkpoint state/files use `private/checkpoints/`; public site artifacts use `private/artifacts/`.

Preview grants bind user/site/immutable revision, last ten minutes, and require fresh membership even after minting. The scoped capability is exchanged for an HttpOnly path-scoped cookie and redirected to a clean URL; it is neither a user access token nor a Vercel/master bypass secret. HTML is sandboxed and cannot connect to external services. Only authorized revision artifact files are served. No checkpoint route exists for users. A separate parse-aware HTML/CSS/srcset projection rewrites static relative and root-relative resources to exact-path asset capabilities; no archived bytes are changed. Each asset capability expires with its parent grant and rechecks membership/site/revision/path. This keeps sandboxed assets working with third-party cookies blocked. The initial top-level cookie is SameSite=None; Secure; HttpOnly and only authorizes read-only revision paths. The preview remains an opaque origin; scripts cannot connect to APIs. Dynamic URLs constructed by JavaScript and dependent resource links inside standalone SVG or advanced unsupported CSS forms are not rewritten; their preview behavior is not claimed. No external resource is fetched or proxied.

## Task 8 contracts

`LeaseAuthority.assertCurrent(tx,workerId,lease)` is transaction-scoped and has **no default production implementation**. It must check fresh revocation, running job, exact worker/generation, unexpired stored lease and current site admission. Ignore request expiresAt. Lock order: site row, worker row, job row, site_operations; sample `clock_timestamp()` after locks. Revocation must hold worker locks; later cancellation/reclaim and fenced site CAS must use compatible order. No object/model/provider work occurs inside SQL transactions.

Controller admission is a bounded 120-second database record. Every write/CAS checks its exact token and server-time expiry. Candidate/job creation transfers admission to the queued job atomically; the following shared-domain enqueue is idempotent. Finally-release removes only its own controller admission. Active jobs block competing edits. Completed/cancelled/needs_attention jobs whose worker ownership ended allow reconciliation/rejection. Task 8 must serialize explicit retry with that same admission rule. Read polling while busy projects durable records and actual job status; idle authorized editing polling reuses the existing core reconciliation/evidence logic.

Upload prepare persists immutable IDs/keys and expectedCheckpointId. Completion rechecks authority and predecessor and creates an **unreferenced** immutable checkpoint; it never advances job progress. Task 8 must atomically commit `job.checkpoint_id`, stage and the matching JSON Job projection with expected predecessor and current authority. Exact commit replay is idempotent; a different delayed predecessor cannot replace newer progress. Older-generation committed checkpoints remain readable to a new owner through a future authorized worker resource route. Add a worker fenced site-CAS entry point; the ordinary repository CAS accepts only a live controller admission and cannot authorize a worker. Private continuation/configuration/recovery tickets remain private.

## Managed devices and durable queue

In the native application, sign in as an administrator to the configured HTTPS control origin, open **Исполнители**, configure a real model, register this device, and explicitly start it. Stop releases cooperative work; remote Pause finishes the current stage before releasing it. Resume requeues this device's paused jobs without erasing checkpoints. Cancel invalidates a job generation and preserves published content. Revocation invalidates the machine credential independently of the administrator session. No online devices means jobs remain queued.

Enrollment is a dedicated main-local native command, not generic renderer dispatch. The fixed sidecar generates a UUID and 32 random bytes (canonical 43-character base64url token). Rust atomically stores the pending descriptor and credential together in the OS secret store before HTTP. The transient administrator access token is never stored. `POST /workers/enroll` takes `{workerId,name,token,controlOrigin}` under a freshly checked administrator bearer and returns only `{workerId,name}`. The server stores only token hash, identity and immutable enrolling-admin/name/origin binding. Exact retries reuse that identity and credential; a different binding conflicts, and revoked identities never revive. A lost HTTP response or ambiguous OS-store write must be retried using the saved pending identity. Rotation is explicit revoke followed by a new enrollment. An existing saved identity is not silently overwritten. Native status returns only safe summary fields. Start, stop and revoke require the renderer's configured expectedOrigin; native code compares it with the saved enrollment before any private sidecar action or bearer forwarding and preserves the saved credential on mismatch. Requests use fixed paths at the configured HTTPS origin and reject redirects.

Claims use `FOR UPDATE SKIP LOCKED`, server time after locks, a 120000 ms lease and at most two live jobs per device. Worker identity comes from fresh token lookup. Every protected mutation checks exact generation, unexpired stored lease and matching site admission in its write transaction. Heartbeat interval is 30000 ms. Upload completion produces immutable unreferenced metadata; only checkpoint CAS with its expected predecessor advances the durable stage. A new owner may read the last committed older-generation snapshot, while the old owner cannot commit. All provider/storage/browser work runs outside SQL transactions.

Worker HTTP uses `POST /worker/jobs/claim` and lease-bound `heartbeat`, `checkpoint`, `finish`, `pause-status`, `pause-boundary`, `site`, `revision`, `catalog`, `snapshot`, `resource`, `artifact`, and `publication` actions under `/worker/jobs/:id/`. User retry/cancel routes are `/sites/:id/jobs/retry|cancel`. Their write transaction checks the locked job kind and fresh membership: editing requires scoped site:edit; generation requires the site owner or an administrator, not assigned read access alone. Classified account/configuration recovery requires an explicit request and exact private checkpoint ticket; retry counters, files and known usage remain intact. Unknown-response retries persist optional `uncertainRequests` separately from known token totals. This is a count of prior attempts with unknown token/billing usage, never estimated charges.

Publication reservation binds immutable request key, manifest/revision/base/checkpoint and originating job or controller. Atomic handoff changes site admission to publication; cancel, expiry or revocation cannot remove that exclusion. Task 9 verifies provider evidence and installs the matching revision/pointer in the server settlement transaction. There is no worker HTTP settlement or worker authority to assert provider success. An exact settlement receipt precedes obsolete lease-bound reads in `runJob`; it also recovers a lost handoff response or settlement while a device was offline without worker revision/pointer/checkpoint writes.

## Vercel publication configuration and continuation

Configure `VERCEL_PUBLICATION_TOKEN` and `VERCEL_PUBLICATION_TEAM_ID` only on the control server, alongside SQL and private R2 configuration. The team identifier is explicit (`team_…`), including the owner's personal Hobby team. The token must be allowed to manage the dedicated Site Factory projects/domains. The server creates deterministic `sf-<site UUID>` projects with Other/framework-null and empty install/build commands; existing projects must have those exact settings and account ownership. Partial configuration leaves the session publish capability unavailable. Workers and renderers receive neither the token nor provider targets or private object keys. No token or bypass header is added to public URLs.

`POST /sites/:id/publication` accepts only `revisionId`, `expectedRevision`, and a UUID `requestKey`. It reuses the shared editing journal/evidence path and requires a current scoped publisher (spec-user or admin), an accepted checked draft and current revision. Request replay returns the same intent. `GET /sites/:id/publication`, `/domain-setup`, and `/publication-history` return scoped safe status, provider-supplied DNS records, and verified external outcomes. History includes initial generation and accepted drafts, distinguishes settlement conflicts, and excludes merely READY deployments. `POST /sites/:id/publication/resume` accepts only the matching intent `id`: owners/admins may resume generation, whereas draft continuation requires current publish permission. Registrar changes remain manual.

Each running managed worker has one throttled publication loop independent of its two generation slots. `POST /worker/publications/tick` has an empty JSON body, requires a current unrevoked machine, and returns only `{ok:true}`. The server selects a due already-authorized intent; the worker cannot select a target or read an unassigned site's private state. Automatic first publication needs no per-site click. When all devices are off, the UI Resume action can advance one bounded step; no offline cron is configured or claimed. `/worker/jobs/:id/publication-receipt` returns only the authenticated machine's exact settled generation binding.

The private normalized ledger links the durable site reservation and editing journal. Unresolved reservations also form a durable attachment outbox: ordinary worker tick, scoped latest/status and explicit Resume recover a handoff interrupted before its provider ledger existed, deriving the exact original job/checkpoint or controller journal binding without the former worker lease or UI request key. Migration005 adds attachment_retry_at; a 15-second attachment retry deadline is written before fallible R2 preparation. Separately from eligibility, ticks select the least-recently-selected eligible reservation using that durable stamp, CAS a new stamp before fallible work, and retain the stamp after attachment. The marker also orders materialized steps; their eligibility still uses provider retry/step deadlines. A failure lasting longer than the worker error wait cannot restore oldest-first priority or starve healthy work across stateless hosts. Scoped status/explicit continuation can retry their authorized reservation. Existing provider records and frozen policy are never rebuilt or overwritten. SQL locks are released before reading R2. Lock order is sites → sorted workers → jobs → site_operations → reservation → provider_publications → provider_accounts. Each server step has a 40-second site/account token; neither SQL locks nor transactions span R2, provider HTTP, or public HTTPS. Both tokens and server expiry fence response commits. Dispatch is journaled before a mutation. Unknown create traverses deployment pages and binds exact metadata; it never blindly repeats create. Unknown project/domain attachment looks up the deterministic identity; an unproven absence remains attention/exclusion. Unknown promotion polls exact alias plus content. Separate account control conservatively allows 60 requests/minute, one concurrent deployment, 100 create attempts/rolling 24 hours, plus provider 429 Retry-After. Quota and DNS waits preserve generated bytes and need no model rerun.

Cancellation prevents undispatched mutations. Accepted/unknown effects retain exclusion until reconciled; accepted building deployments retain account capacity until terminal readiness. A promotion already accepted may change public traffic. Verified exact success installs the observed pointer when the expected revision/reservation still match, even if the job remains cancelled. Conflicting CAS preserves external evidence/reservation and reports attention. No automatic rollback is performed. Future retention must preserve active/unresolved intents, their original manifests/checkpoints, revision ancestry and editing journals; no GC is introduced here.

The server verifies R2 bytes/digests and uploads them through `/v2/files`, then creates `/v13/deployments` with uploaded SHA references and no target. A publisher-owned root `vercel.json` carries restrictive global CSP/nosniff/no-referrer headers. It has a separately frozen policy version/hash; generated configuration is rejected, never merged. Archive/preview bytes remain unchanged. REST promotion uses `/v10/projects/:projectId/promote/:deploymentId`; a 201/202 response is not publication success. Exact project/deployment/alias metadata and public HTTPS index bytes/headers must match before settlement.

The reusable server-only HTTPS verifier admits canonical registered hosts on port443, rejects special-use IPv4/IPv6 DNS results, pins a validated address with the original TLS hostname, and uses an isolated proxy-free agent with normal CA verification. Limits are 10 seconds total, 1.5 seconds DNS, 3 seconds headers, 16KiB headers, two same-host HTTPS redirects and 4MB streamed bytes (also limited to the expected artifact length). Every redirect is re-resolved/revalidated. Wrong content, encoding, CSP, alias, TLS or network evidence fails closed. This is point-in-time evidence; later external DNS/provider changes are not an atomic guarantee.

## Batch imports and registry pagination

Apply migration006 after005 before using import routes. POST /batches/commands accepts only the versioned allowlisted method/params DTOs from contracts/import.ts; session role is resolved on the server. Source CSV/XLSX and user-selected PNG resources use owner-bound identities,24,000-byte chunks, contiguous part numbers, total size and SHA-256 verification. No whole workbook or5000-row JSON body is accepted. Source maximum16MiB; XLSX expansion64MiB,256entries,5000data rows,16coordinate columns,8000UTF-16 units/cell; only domain/about/referenceId/logo headers are supported. XLSX accepts one worksheet and rejects formulas as row issues, macros, encryption, external links, DTDs, duplicate paths/cells and unsupported ranges. Parser elapsed checks are cooperative; they do not claim OS process isolation. PNG decoding checks signature/CRC and limits2MB/2048pixels before allocation. Logo URLs are never fetched.

Prepare persists paginated preview rows and original source chunks. Row correction and local logo selection advance draft revision; typed canonical fingerprints avoid JSONB key-order equality problems. Commit binds actor/requestKey/revision/payload and returns only batchId. It admits at most25 rows, then local scheduler or the managed worker tick continues bounded durable admissions. Every successful row reserves canonical domain, site, generation job, operation and batch association in one short transaction. Exact replay keeps identities; existing domains become row errors. Per-row Retry uses the same generation job and the existing explicit provider-recovery checks. Pause waits for a saved boundary, Resume affects paused jobs, terminal attention/provider waits are not restarted automatically, and cancellation retains publication reservations/outcomes. Admission and publication continuation run independently so one failure cannot prevent the other attempt.

Batch access is explicit owner/admin/assignment scope; access to one child never grants the parent or sibling rows. Admin assignment grants current and future child site visibility and normal role-dependent editing. Batch-derived grants stay separate from direct site grants, including real RLS, so revocation cannot erase independent access. Conveyor controls stay owner/admin and target only the batch generation jobs; later edits remain separate.

Site list supports domain/status/batchId server filters and bounded keyset pages. Existing unfiltered UUID cursors remain compatible; filtered cursors bind principal/role/filter. Registry pages use a1,000,000-byte prefix budget in addition to row limits; previews/results use5rows of bounded named fields (no arbitrary raw16-column objects), and batch lists use50small summaries. Stored originals are retained without display truncation.

Migration006 also replaces only the claim candidate query's scan bound: LIMIT1 before FOR UPDATE SKIP LOCKED. The inherited PL/pgSQL cursor otherwise prefetches and locks unrelated sites before device capacity serialization. Its SECURITY DEFINER/search_path/grants, signature, server clock, lease duration, publication exclusion and lock order remain unchanged; migration003 is untouched. The deterministic SQL lock-barrier regression proves one locked/three available candidates plus unique claims/cap/refill.

Task12 recovery requires server DATABASE_CONNECTION_MODE=direct or session for the same DATABASE_URL. Unknown/transaction modes fail snapshot issuance before any session advisory lock; ordinary application/export paths remain available. Use the actual provider direct/session endpoint ([Supabase limitations](https://supabase.com/docs/guides/database/connecting-to-postgres)); do not guess from port/URL. vercel.json enables Fluid compute and functions.api/index.ts.maxDuration=240, preserving the existing rewrite.
