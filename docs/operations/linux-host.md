# Linux-хост для публикации с Windows VPS

## Актуальная целевая инфраструктура

Уточнение пользователя: дальнейшее размещение — на выделенных серверах OVHcloud под Linux, расчётный масштаб — до 256 сайтов, каждому отдельные IPv4 и IPv6. Windows VPS остаётся управляющим узлом и исполнителем генерации. Существующий Linux VPS используется как пилотная инфраструктура до переноса.

256 сайтов — целевая ёмкость проекта, а не автоматически доступный пул. Адреса выделяются только из фактически назначенных серверу IPv4 и маршрутизируемого IPv6-префикса. Лимиты и сетевой профиль проверяются для конкретного тарифа; нельзя переносить Netplan-параметры VPS на dedicated без проверки интерфейса, шлюза и маршрутов. Публикация IPv6 потребует AAAA, привязки Nginx и внешней проверки IPv6/TLS; текущий IPv4-конвейер ещё не реализует эти операции.

Официальные источники: [лимиты Additional IP](https://us.ovhcloud.com/network/additional-ip/), [IPv6 на dedicated](https://docs.ovhcloud.com/en/guides/bare-metal-cloud/dedicated-servers/network-ipv6).

Этап подготовки инфраструктуры разрешён пользователем 4 ноября 2026: SSH-ключ и дальнейшая настройка без повторных подтверждений. Подготовлен один OVH VPS; домены и DNS на этом этапе не изменяются.

## Доступ

`scripts/enroll-linux-host.mjs` получает первоначальные credentials через stdin JSON. Создаёт Ed25519, сохраняет приватную часть через Windows DPAPI LocalMachine в отдельной конфигурации внутри `.local-state/server/ssh`. Каталог наследует закрытый ACL серверных данных: SYSTEM и локальные администраторы. Приватный ключ не записывается открытым текстом, не передаётся клиентским приложениям и не входит в Git. Перед запуском нужна сборка серверного `secrets.js`.

Публичный ключ добавляется в существующий `authorized_keys` пользователя `ubuntu`, с `from="<IPv4 управляющего сервера>",restrict`. Это разрешает выполнение команд с управляющего Windows VPS, запрещает forwarding и PTY. Доступ через sudo проверяется отдельно; это административный ключ, а не изолированный аккаунт сайта. Прежние ключи и парольный вход сохраняются. Изменение исходящего IPv4 требует обновления ограничения через альтернативный доступ.

SSH всегда проверяет закреплённый SHA256 отпечаток сервера. Автоматическое принятие неизвестного или изменившегося ключа отключено. Пароль для последующих операций не нужен.

## Проверка

```powershell
node scripts/verify-linux-host.mjs .local-state/server/ssh/ovh-pilot.json
node --test scripts/test/linux-ssh.test.mjs
```

`verify-linux-host` проверяет вход по ключу, sudo, Nginx, адреса и firewall. Проверка также выполнена отдельной задачей SYSTEM — той же учётной записью, под которой работает управляющая служба. Временная задача удаляется после проверки.

## Сеть

`scripts/configure-linux-ipv4.mjs <host.json> <inventory.json> <interface>` принимает только адреса с состоянием Assigned и привязкой к нужному сервису. Создаёт отдельный Netplan overlay, сохраняет резервную копию и ставит таймер отката на 180 секунд. Подтверждение — независимый SSH-вход по каждому адресу, после чего таймер выключается. При ошибке таймер остаётся активным. Существующий overlay скрипт не заменяет: это намеренная защита от неявной смены адресов.

Netplan YAML имеет права 600. Перед генерацией используется umask 022: иначе Ubuntu 26.04 может создать runtime `.network` с правами, при которых systemd-networkd не сможет прочитать его. В ходе настройки это обнаружено и исправлено; проверены основной IPv4, пять дополнительных и сохранение IPv6. Перезагрузка не проводилась.

## Веб-сервер

`scripts/linux-host.mjs <host.json> scripts/linux/prepare-web-host.sh` устанавливает Nginx, подготавливает `/srv/site-factory/sites` и `/srv/site-factory/acme`, включает автозапуск и UFW с TCP 22/80/443. Исходящие соединения разрешены. У firewall есть таймер отключения на 180 секунд: после независимой проверки SSH и HTTP оператор должен остановить `site-factory-firewall-rollback.timer`.

Default virtual host возвращает 404. Подтверждён HTTP по всем шести IPv4 с Windows VPS. Открытый TCP 443 не означает готовый HTTPS: сертификаты и TLS virtual hosts ещё не настроены.

## Публикация из приложения

Подключена 4 ноября 2026 по прямому поручению пользователя. `apps/server/src/hosting.ts` ведёт назначения и задания в таблицах `factory.hosting_addresses`, `factory.hosting_sites`, `factory.hosting_jobs`. Полные права одинаковы у всех активных пользователей. HTTP API требует сессию и CSRF. Работа продолжается после закрытия приложения и после перезапуска службы. Запуск операций сериализован PostgreSQL advisory lock; на Linux дополнительно используются flock и монотонный номер задания, чтобы устаревший запрос не заменил новую версию.

В редакторе доступны первая публикация, обновление, выбор предыдущей успешной версии и ручная смена IPv4. Статусы отображаются в редакторе, списке сайтов и заданиях. SSH- и DNS-секреты не передаются клиенту. Новые домены подключаются через выбранный DNS-провайдер после проверки доступа к зоне. Абсолютное исключение защищённого домена и его поддоменов сохранено в приложении и Linux-обработчике. В этой установке один Linux-хост, шесть IPv4; сайты не распределены заранее.

`scripts/linux/publish.py` устанавливается root-owned в `/usr/local/lib/site-factory/publish.py`. Он проверяет идентификаторы, домен, адреса, пути, размеры и SHA256 файлов, создаёт неизменяемый release, атомарно переключает ссылку `current`, проверяет Nginx и HTTP. При ошибке переключения восстанавливает прежние ссылку и конфигурацию. Версии, явно выбранные для публикации, закрепляются от очистки файлов в PostgreSQL и сохраняются на Linux. Команда очистки оставляет текущую и пять последних успешно опубликованных версий. После подтверждения очистки на Linux снимаются закрепления старых файлов; откат к исключённым версиям скрывается. При отказе Linux закрепления сохраняются.

Ручная замена IPv4 резервирует новый адрес и меняет A-запись. Старый адрес продолжает обслуживать тот же сайт для посетителей с закэшированным DNS; освобождение запускается отдельной командой после ожидания минимум 48 часов и прежнего TTL. Проверяются отсутствие A-записей со старым IP, распространение текущего DNS и HTTPS новой версии; затем удаляются старые привязки Nginx и адрес возвращается в пул. IPv6 и www автоматически не меняются: публикация обслуживает корневой домен. Конфликтующие корневые AAAA/CNAME/ALIAS останавливают задание с объяснением.

Namecheap использует POST, DPAPI-ключ и фиксированный исходящий IPv4 Windows VPS. Перед записью сохраняются полная прочитанная зона и план в задании. Алгоритм сохраняет MX/TXT и поддомены, перечитывает зону непосредственно перед записью, проверяет результат. У Namecheap нет атомарного compare-and-set: одновременные изменения зоны вне приложения между последним чтением и записью остаются ограничением API. Внешнее изменение, обнаруженное до записи или при проверке, останавливает автоматизацию. Откат сайта меняет файлы, а не восстанавливает устаревший снимок всей DNS-зоны.

После распространения A через два публичных резолвера выполняется Certbot webroot для корневого домена. HTTPS проверяется с SNI и доверенной цепочкой сертификата, без отключения проверки TLS. HTTP также остаётся доступным по IPv4. Автопродление — `certbot.timer` и deploy-hook с `nginx -t`/reload. В момент завершения задания проверяется конкретная версия по HTTPS; затем серверный монитор периодически повторяет DNS/HTTP/HTTPS-проверку версии и проверяет срок сертификата. Предупреждение о сертификате появляется за 14 дней.

## Приёмка

`scripts/test-server.mjs`: авторизация, генерация и публикация с фикстурами; конкуренция за IP, перезапуск на этапе DNS, обновление, откат, замена адреса, сохранность MX/TXT и остановка при внешнем изменении DNS. `scripts/server-browser-smoke.mjs`: кнопка публикации и итоговый статус в интерфейсе.

`scripts/hosting-live-smoke.mjs` выполняет **реальные внешние изменения** на `chinazes.space`: временный технический сайт, Namecheap, сертификат, обновление и откат. Применять только в явно разрешённом окне проверки. Он требует свободный тестовый IPv4, сохраняет DNS-снимки в защищённом каталоге, использует отдельную базу и восстанавливает DNS только если зона не изменилась извне. `scripts/cleanup-hosting-live.mjs <каталог результата>` удаляет только проверенную временную установку после подтверждённого восстановления DNS.

Живая приёмка 4 ноября 2026 прошла полностью. Исходная DNS-зона восстановлена; тестовый сайт и сертификат удалены. Публикации пользователя не создавались. Первую рабочую публикацию можно запустить после генерации сайта кнопкой «Развернуть сайт».

## Несколько серверов и DNS-провайдеров

Раздел «Серверы» принимает публичный IPv4, SSH-порт, логин, пароль либо приватный ключ, дополнительные назначенные провайдером IPv4 и необязательный ожидаемый fingerprint. Поддерживаются пустые Ubuntu 22.04+ / Debian 12+ с Python 3, systemd и root либо sudo без пароля. Первое подключение без переданного fingerprint использует TOFU; сохранённый отпечаток автоматически не заменяется.

Серверная очередь хранится в factory.hosting_hosts. Создаётся отдельный Ed25519-ключ, ограниченный исходящим адресом управления. Bootstrap-секрет и рабочий ключ зашифрованы DPAPI; bootstrap удаляется после проверки рабочего ключа. Ошибочный логин/пароль можно исправить в интерфейсе на этапе подключения. В ответах API приватных ключей нет.

Подготовка: проверка пустого сервера, Nginx/UFW/Certbot, дополнительные IPv4 /32 через Netplan, firewall, независимые SSH/HTTP-проверки. Network/firewall защищены таймерами отката 180 секунд. При повторе сначала восстанавливается незавершённый этап. NAT и неизвестная структура Netplan останавливают автоматизацию. IP появляются в публикации только после готовности сервера. Уже подключённый OVH импортируется без повторной настройки сети.

Публикация выбирает готовый host_id и закрепляет его вместе с IP. Замена IPv4 допускается на том же VPS; перенос на другой готовый сервер доступен отдельно: старая привязка сохраняется до успешной проверки новой публикации по HTTPS. Старый IPv4 остаётся в ожидании освобождения. Генерация остаётся на Windows VPS.

DNS домена хранится в factory.hosting_domains, провайдер фиксируется также в каждом задании. GoDaddy — значение по умолчанию для новых доменов, восемь прежних пилотных доменов сохраняют Namecheap. GoDaddy использует Domains v3, Personal Access Token с правами domains.domain:read и domains.dns:update. Токен сохраняется DPAPI. Адаптер читает всю зону с пагинацией, изменяет только одну A-запись @ по recordId (либо создаёт её), TTL 600. Несколько исходных A-записей @ требуют предварительного ручного выбора одной; MX/TXT/SRV/CAA и поддомены не перезаписываются. Снимки до/после сохраняются. Изменения вне приложения обнаруживаются повторным чтением; атомарного compare-and-set у API нет.

Спецификация GoDaddy: https://developer.godaddy.com/openapi/domains-v3.json ; авторизация: https://developer.godaddy.com/en/docs/api-users/auth . Интеграция проверена моками по схеме API; реальный аккаунт GoDaddy пока не подключён. Автоподготовка второго пустого VPS проверена симуляцией отказа/возобновления, не на втором реальном сервере.

## Обслуживание подключённых серверов

В разделе «Серверы» можно добавить уже выделенные провайдером IPv4, проверить узел, изменить SSH-параметры, заменить ключ, запретить новые размещения и вывести пустой узел из конвейера. Вывод не удаляет VPS и не отменяет оплату. Занятые адреса блокируют вывод. Во время обслуживания новые публикации на узел блокируются.

Смена подключения сохраняется только после проверки входа и рабочего ключа; отпечаток SSH закреплён. Ротация сначала устанавливает новый ключ и проверяет вход, затем сохраняет его и удаляет старый. Прерванный этап удаления можно повторить после перезапуска. Добавление IP использует таймер сетевого отката и независимые проверки. Покупка и удаление IP у провайдера не выполняются.
