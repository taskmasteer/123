# Versions, source export and independent recovery

An administrator creates a backup from **Резервные копии** in the desktop application, enters a new passphrase, waits for verification, then saves the encrypted file with the native chooser. Keep the file and passphrase separately. Test restoration into a fresh installation periodically. A version in R2 is dependent on the original account, database and credentials; it is not this independent backup.

Version history retains the current successful publication and five preceding successful publication actions. A rollback is a new action through the existing publisher admission, frozen reservation, provider verification and settlement flow. Returning to the same bytes counts as another action. Drafts, active candidates/jobs, unresolved external effects, snapshot/read pins and installed catalog resources are additional roots. Old ambiguous timestamps are labelled and conservatively protected. Immutable metadata, checkpoint digests and provider evidence remain after payload collection. Unreferenced payloads require an observed24-hour grace period and a second fenced check. Detailed accepted checkpoint payloads have a separate30-day minimum; they can contain old snapshot bytes during that period. Durable latest-per-job usage remains after detail removal: transcript totals plus the active cumulative continuation once, with unknown/uncertain coverage preserved.

Administrators can open a site's original source tree, read text, download a file, or save a ZIP. The ZIP contains original static hosting paths and bytes. It is suitable for another static hosting service. It contains no checkpoint state or application credentials. A fresh administrator session is checked for each limited native handle or server snapshot resource read; role loss or session expiry invalidates further access.

## Backup v1 scope and technical bounds

V1 restores **local→fresh local** and **managed→fresh managed**, including a different machine, installation and configured object store. Local/managed conversion requires a separate future migration. An authenticated adapter/schema mismatch fails before target installation. Credentials, Auth login sessions/invitations, provider/API keys and reusable worker tokens are excluded. Verified validation PNGs, retained original source, private checkpoint detail still available, immutable evidence, usage, batches, publication provenance, catalog settings and exact pinned template/reference bytes are included. Historical missing required PNGs or pinned content make a full backup unavailable until verified backfill; placeholders are never invented.

The fixed64-byte `SFBAK001` header is authenticated AES-256-GCM additional data. Scrypt has fixedN131072/r8/p1,16-byte salt,32-byte key and256MiB maximum working memory; passwords occupy8–1024UTF-8 bytes. The12-byte nonce and16-byte tag are fixed-size. Names, metadata and content are encrypted. Authentication must finish before ZIP parsing or extraction. No password passes through ordinary control HTTP, settings, selection snapshots or logs. Desktop main-window ACL and a dedicated private pipe carry the transient value.

One envelope permits at most48GiB of ZIP plaintext, below AES-GCM's per-message limit of2^36−32bytes; streaming does not make one invocation unlimited. Additional bounds:1million ZIP entries,500000 metadata records/256MiB total,32MiB per member,<=1MiB authenticated index chunks/192MiB total. Every file size/hash and complete dependency closure is checked; excess capacity, missing/extra members, unsupported compression, unsafe paths, symlinks, duplicates or mismatched hashes fail explicitly. No partial success or5000-site truncation is returned. Free private staging space is needed for the encrypted file, authenticated plaintext, extracted members, staged target and bounded disk indexes. Snapshot handles expire after1hour and desktop operations after30minutes; expired sessions require a new operation. These are technical resource bounds, not generation spending limits.

Capacity evidence is distinguished in the task report: an actual5000-record SQL snapshot; synthetic5000×6-state projected inventory (210000retained source/PNGs plus60000detailed checkpoint objects,485000metadata/755000archive input entries,~13.7GB projected bytes); actual bounded disk descriptor indexing; and separate real small encrypted/local/managed roundtrips with the original source removed. A48GiB body has not been exercised.

## Fresh local target

Use **Проверить и восстановить копию**, choose the file, then inspect its verified contents. Restoration creates a private fresh root; it does not overwrite the active database. The staged SQLite database is reopened, relational bindings and all available payloads are verified, then an atomic root selector is installed. Restart the application. A failed stage is removed; a failure after a complete stage leaves `.restore-status-<id>.json` and `.restored/<id>` for operator inspection. The previous root and selector remain recoverable. Never manually combine databases or change a selector to an unverified directory.

Completed/cancelled jobs remain terminal. Resumable work is paused with lease generation advanced. New generation, mutating status recovery and visual Save autoaccept are blocked while recovery quarantine exists. Review sites and pending actions before **Проверка завершена — разрешить работу**. Resume selected paused work explicitly; do not regenerate completed sites merely because they were restored.

## Fresh managed target

1. Provision an empty configured target with migration008 and a verified bootstrap Auth administrator. It must contain no existing site, job or artifact installation. Configure fresh provider/storage credentials separately.
2. Invite destination Auth users with the normal privileged invitation workflow; verify their destination identities. Supply explicit1:1 source→destination Auth UUID mappings in the restore review. Source emails alone are not identity proof. Only named Auth fields (including the original visual Save actor) are remapped. Semantic IDs, replay/hash fields, publication bindings and source external evidence are preserved. New physical storage keys have separate source provenance.
3. Restore the verified copy. Objects are staged under new private keys; logical metadata is validated in bounded pages. A short exclusive database installation transaction activates the complete closure. Missing objects or invalid mappings leave the target site/job/artifact installation unchanged. Private `recovery_snapshots`/`recovery_snapshot_records` retain the restore ID, staged metadata/object mappings and failure remnants for operator inspection (a failed native operation reports that ID); verified raw object chunks are removed as each object completes, with at most 64 MiB in-flight object staging and 256 MiB metadata staging; do not mistake staged objects for an active installation.
4. Re-enrol workers and issue fresh tokens; restored logical worker IDs remain revoked and their old hashes unusable. Review ownership, memberships, assignments, pinned versions and publication accounts. Original completed/cancelled jobs stay terminal; active work is paused. Quarantine also blocks tick/claim/resume and GET recovery/visual autoaccept.
5. **Retire or disable the original control authority before releasing the fresh target. Revoke or rotate its provider credentials if the old installation can still run.** Independent databases do not share leases and cannot fence each other. A normal additional device logs into the **same** managed authority; it does not restore a second active database.
6. Open the restored publications list in **Резервные копии** and use **Сверить публикацию** after confirming the source authority has been retired. Each read-only reconciliation binds the restore ID, original reservation/evidence digest, frozen publication and verified configured provider account. The server reads the account, project, deployment, alias and public HTTPS content; it sends no create, upload, promote or delete request. Only positive terminal evidence can settle the original publication or cancel its original reservation through the existing publisher. A repeated completed reconciliation returns its recorded result. Ambiguous, unattached or unverifiable effects return a concrete manual-required result and retain quarantine/exclusion. An administrator acknowledgement is not provider proof. For genuinely unverifiable out-of-band effects, keep the authority quarantined, retain original evidence and resolve the exact frozen account/project/deployment with the hosting operator; do not clear rows with SQL or reconstruct a different active mutation. The release API refuses unresolved reservations and requires the retirement acknowledgement.
7. Release quarantine only after those checks. Resume a supported pending operation explicitly and check its fresh bindings; restored pending visual Save uses its verified mapped original saver. Restore uses the original accepted immutable evidence after detailed checkpoint cleanup. Account drift or unsupported old bindings require a concrete reconciliation/reconfirmation, never a guessed mutation.

Actual Windows11/macOS14 chooser, packaging/credential ACL, physical devices and live-provider acceptance belong to Task14. The implementation tests use isolated local SQL, pure native schema tests, mocked private chooser boundaries and headless Chromium.

Current installed catalog versions are an explicit recorded set, with exact immutable version-to-bundle edges. Backup reads and stale worker uploads cannot move that pointer. Superseded bundles remain only while an active/retained state or pin needs them, then follow the same observed grace protocol.

On upgraded stores, accepted checkpoint pointers, durable accepted markers and explicit recovery tickets prove legacy acceptance; file presence does not. Verified backfill registers physical hashes, evidence and typed edges, and changes per-job usage only for the latest accepted checkpoint. Unknown local envelopes retain their acceptance-unknown provenance and at least 30 days of detail. A missing/unsupported closure blocks cleanup for that subject and makes full backup unavailable until repaired. Metadata IDs/hashes are retained after eligible payload deletion; a new reference cannot revive a tombstone.

The authenticated archive descriptor index and logical record/payload/path closure checks use bounded private SQLite staging. Ordered metadata pages contain at most 64 descriptors; logical restore installation batches contain at most 50 local or 20 managed rows. No installation-sized metadata array is reconstructed. Source snapshot/read capabilities, live pins and earlier materialized snapshot copies are excluded from logical backup; destination operations receive fresh handles. Actual measured descriptor iteration and logical validation are reported separately from projected large blob volume.
