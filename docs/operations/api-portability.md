# Установка и перенос API Site Factory

Управляющий API работает на Windows x64 и Linux x64 (Ubuntu/Debian с systemd).
Домен не требуется. Клиенты подключаются по HTTPS к публичному IPv4 и проверяют
сертификат из файла `.sfconnection`. Открыть у провайдера нужно TCP 9443;
PostgreSQL слушает только 127.0.0.1:54329.

## Новая установка

Распакуйте API-пакет в отдельный постоянный каталог, например `C:\SiteFactory` или `/opt/site-factory`. Не распаковывайте поверх
существующей установки. Пакет содержит собранный API, шаблоны, миграции и
установщики; Windows-пакет также содержит PostgreSQL 18. Нужен доступ к интернету
для установки Node.js и зависимостей. Windows: Server 2019 или новее; Linux:
актуальная поддерживаемая Ubuntu/Debian x64. Установщик Linux добавляет официальный
репозиторий PostgreSQL и создаёт отдельного системного пользователя sitefactory.

Windows, PowerShell от администратора из папки пакета:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-api.ps1 -PublicIPv4 203.0.113.20
```

Linux, каталог без пробелов, например `/opt/site-factory`:

```bash
sudo bash scripts/install-api.sh 203.0.113.20
```

Замените пример IP на настоящий адрес сервера. Установщик запросит логин и пароль
первого пользователя; пароль не нужно передавать в командной строке. После
установки заберите `site-factory.sfconnection`. На странице входа клиента нажмите
«Изменить сервер — импорт файла», выберите файл и проверьте показанный адрес.
Клиент проверит доступность API и сертификат, сохранит подключение и вернётся
на страницу входа. Файл не содержит паролей, API-ключей или закрытого TLS-ключа.
Получать его следует от владельца API: файл определяет, какому серверу доверяет клиент.

## Перенос Windows ↔ Linux

1. В приложении откройте резервные копии. Сохраните архив `.sfbak` и отдельно ключ
   восстановления. Для аварийного восстановления они должны храниться вне старого сервера.
2. При плановом переносе завершите текущие операции, закройте доступ к новым
   заданиям и создайте окончательную копию. Затем остановите службу старого API.
   Уже опубликованные сайты продолжают работать на своих серверах.
3. На новом сервере распакуйте пакет и запустите установщик с архивом:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-api.ps1 -PublicIPv4 203.0.113.20 -BackupFile C:\Backup\factory.sfbak
```

```bash
sudo bash scripts/install-api.sh 203.0.113.20 /path/to/factory.sfbak
```

4. Введите ключ восстановления. Восстановление создаёт новую базу и отдельный
   каталог, пересохраняет секреты под защитой новой машины и отзывает старые сессии
   и приглашения. Пользователи и их пароли сохраняются. Исполнители остаются на паузе.
5. Разрешите новый исходящий IPv4 в Namecheap и обновите ClientIp в настройках
   Namecheap приложения. Для GoDaddy проверьте права сохранённого токена.
6. SSH-ключи серверов сайтов могут содержать ограничение `from="старый_IP"`.
   Пока восстановленная установка на паузе, откройте «Серверы → Изменить подключение SSH»
   и укажите аварийный пароль или ключ. Проверка сохранённого отпечатка обязательна;
   операция обновит ограничение источника и проверит автоматический ключ. Она разрешена
   на паузе и не запускает публикации. Если нет аварийного входа, нужна консоль провайдера.
7. Передайте новый `.sfconnection` клиентам. Войдите прежним логином и паролем,
   проверьте серверы и DNS, затем снимите паузу восстановления в приложении.
   Перед снятием паузы API сверяет версии, адреса и порядок операций на известных Linux-сайтах.
   Более новая удалённая версия импортируется в историю; при несовпадении IP восстановление
   остаётся на паузе. Неопределённые внешние операции не повторяются вслепую. Старый и новый API нельзя одновременно запускать с
   одной восстановленной очередью.

При восстановлении используется runtime установленного API-пакета, а шаблоны,
файлы и библиотека — из копии. Используйте пакет той же или более новой версии.
Архивы прежнего Windows-формата поддерживаются; секреты Windows DPAPI расшифровываются
при создании архива на старой машине, а не на новом Linux-сервере.

## Смена IP и обслуживание

Адрес меняется в остановленном API с помощью `server-manage.mjs address --ip IP`
(Node находится в `.local-state/tools/node`, Linux: `bin/node`). Восстановленная
установка автоматически определяется по `active-data.txt`. Команда выпускает
новый сертификат и файл подключения. Затем запустите службу и импортируйте файл
в клиентах. Это также способ обновить сертификат по истечении его двухлетнего срока.

Windows: задача `SiteFactory-API` в планировщике, журнал `server.log` в активном
каталоге данных; отдельная служба базы `SiteFactory-Postgres`. Остановка API
сохраняет базу запущенной. Linux:
`systemctl status site-factory-api`, журналы `journalctl -u site-factory-api`.
У старой установки из разработки задача называется `SiteFactory-Control`.
Остановку старой установки нужно делать по её фактическому имени.

Ключ Linux `.local-state/server/master.key` имеет права 0600 и принадлежит пользователю
службы. Его не переносят вместе с зашифрованными строками базы: для переноса используется
архив и ключ восстановления. Нельзя заменить master.key в действующей установке.

Внешнее хранилище нужно настроить отдельно; локальная копия не защищает от потери управляющего сервера.
Сборка пакета разработчиком: `node scripts/build-server.mjs`, затем
`node scripts/package-api.mjs` для Windows и `node scripts/package-api.mjs --linux`
для Linux. Рабочая база и конфигурация с секретами в пакет не входят.

Установщики также устанавливают Chromium и проверяют его запуск с включённой
песочницей. На Ubuntu с ограничением user namespaces создаётся отдельный профиль
AppArmor для Chromium этой установки; глобальное ограничение не отключается.
Windows-установщик ставит подписанный Microsoft Visual C++ runtime по
[официальной ссылке Microsoft](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist/).


## Обновление установленного API и откат

Выпуск 0.6.0 содержит updater для проверенного перехода 0.5.0/0.6.0 → 0.6.0.
Это политика совместимости только этого выпуска, а не разрешение откатывать любую будущую схему.
Updater предназначен для установленного API-пакета; он отказывается менять рабочую Git-копию.

Архив и соседний файл `ARCHIVE.json` должны поступить вместе. Проверка использует
доверенный публичный ключ уже установленного приложения:

```text
node scripts/verify-api-package.mjs /path/to/SiteFactory-API-windows-x64-0.6.0.zip
```

Завершите текущие задания. Обновление выполняется одной командой от администратора:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\update-api.ps1 -Archive C:\Downloads\SiteFactory-API-windows-x64-0.6.0.zip
```

```bash
sudo bash scripts/update-api.sh /path/to/SiteFactory-API-linux-x64-0.6.0.tar.gz
```

Linux: архив и его `.json` должны быть доступны пользователю `sitefactory`.
У старой Windows-установки укажите `-TaskName SiteFactory-Control`.

Сценарий останавливает API, оставляет PostgreSQL работающим, проверяет подпись и платформу,
подготавливает зависимости и проверяет Chromium. Затем создаёт зашифрованную резервную копию,
меняет только код и зависимости, сохраняет старый выпуск и запускает API. Если новый процесс
не проходит проверку готовности, сценарий возвращает предыдущий код и запускает его.
Адрес, TLS, пользователи, пароли, объекты и база не переносятся и не заменяются.

Журнал `.local-state/upgrade.json` позволяет восстановить прерванную замену. Незавершённая
замена отменяется при следующем запуске updater. Для ручного возврата кода остановите API,
выполните `node scripts/update-api.mjs rollback`, запустите службу и проверьте готовность.
Архивы данных и старый код не удаляются автоматически. Для несовместимой будущей версии
нужна отдельная политика миграции/восстановления; updater откажет до изменения установки.

## Внешняя резервная копия

Поддерживается отдельный смонтированный диск или сетевой каталог:

```text
node scripts/server-manage.mjs backup-target --directory E:\SiteFactoryBackups
```

Каталог должен быть доступен учётной записи службы (Windows: LocalService; Linux: sitefactory).
Пользовательский сетевой диск Windows не обязательно виден службе. Для сетевого хранилища
настройте доступ службы, а не общедоступную папку без аутентификации.
Копируется только зашифрованный `.sfbak`; размер и SHA-256 сверяются до завершения.
В приложении отдельно видно, подтверждена ли вторая копия. Ошибка копирования не удаляет
успешный локальный архив. Сам по себе другой путь на том же физическом диске не является
аварийной защитой. S3 напрямую этим вариантом пока не поддерживается.

## Диагностика и права

- Windows API и PostgreSQL: LocalService, без административного токена. PostgreSQL имеет
  отдельную службу и правила автоматического перезапуска. Для существующей разработки есть
  `scripts/migrate-windows-service.ps1`; запускать после резервной копии при пустой очереди.
- Linux API и PostgreSQL: отдельные systemd units, пользователь sitefactory.
- API подключается к БД под выделенной runtime-ролью без CREATE DATABASE, SUPERUSER и чтения
  файлов PostgreSQL. Миграции и резервирование используют защищённые операторские данные.
- Внешний watchdog следит за API; журналы ограничены по размеру (10 МБ, пять архивов).
- `/health/live` показывает работоспособность процесса; `/health/ready` — доступность БД.
  В приложении есть состояние исполнителя, последней копии и срока TLS-сертификата API.
- При предупреждении о сертификате замените его и передайте новый `.sfconnection` заранее.
  Одновременное доверие двум сертификатам пока не реализовано; требуется плановое окно замены.
- Лимиты DeepSeek: `SITE_FACTORY_JOB_TOKEN_BUDGET` и `SITE_FACTORY_BATCH_TOKEN_BUDGET`.
  По умолчанию 16 000 000 и 4 096 000 000 единиц. Это консервативный верхний предел
  (UTF-8 байты запроса + максимальный ответ), а не счёт провайдера в долларах.
  Резервирование атомарно, не сбрасывается перезапуском; неясные/неудачные запросы тоже учитываются.
- Сброс забытого пароля: `node scripts/server-manage.mjs reset-password`. Пароль вводится
  скрыто, все сессии пользователя отзываются. Email не нужен.

## Выпуск и проверки

Подпись обновлений клиента и API — Ed25519; закрытый ключ издателя хранится вне установки
API. Пакеты без ключа подписи считаются сборками разработки и не проходят production-проверку.
Windows Authenticode — отдельная опция `SITE_FACTORY_SIGN_CERT_SHA1`; без сертификата издателя
EXE остаётся без Authenticode. Подпись manifest не следует называть Authenticode.

Общий gate: `npm run verify`. Изолированная PostgreSQL поднимается автоматически.
Дополнительно: `node scripts/api-install-smoke.mjs`, `node scripts/client-smoke.mjs`,
`node scripts/reference-template-smoke.mjs`. Для CLI проверки обновления задайте
`SITE_FACTORY_TEST_UPGRADE_ARCHIVE` на подписанный архив текущей платформы.
Нагрузочные сценарии по умолчанию проверяют 256 сайтов; `SITE_FACTORY_EXTENDED_SCALE=1`
включает старый расширенный сценарий на 5000. Он не является подтверждённой ёмкостью продукта.
