# Bounded recovery transfer and resumable preparation

Task15 replaces the managed native per-record HTTP loop and separates preparation from activation. It preserves `createBackup`, `restoreBackup`, `ExportHandle`, `RestoreReport`, the private native commands, and the encrypted archive codec. No archive format, provider, service, dependency, or application workflow is added.

## Measured problem and interfaces

At reviewed base `2d2a9e4`, `NativeArchives` required at least900009 metadata GETs and1800018 metadata staging/completion POSTs for the representative5000-site/six-state installation. File bodies additionally used24KB calls; `/install` performed every SQL remap, body/evidence check and prepared INSERT inside one HTTP request. At an **assumed**10ms round trip, the metadata GETs alone would take9000.09s. This arithmetic is conditional, not a measured network result.

The actual Task12 normalized source contained630008 logical rows,270000 physical descriptors,900009 expanded metadata records and532154933B serialized metadata. Its13.5GB bodies were a projection. Task15's valid smaller-body fixture retains the same logical/descriptor counts and measures its own different metadata/body bytes. It does not write/extract900k encrypted archive members or claim13.5GB throughput. A separate real encrypted native/inspection roundtrip covers codec/orchestration compatibility.

`packages/contracts/src/recovery-transfer.ts` owns strict DTO parsers. A frozen binding contains protocol version, transfer ID, source ID, record count and digest. A metadata/resource part contains ordinal, offset, full size, SHA-256, canonical Base64 and completion marker. A page adds cursor, next cursor, an authorized metadata-window resource cursor and live expiry. Preparation progress contains binding, phase, prepared/total counts and cursor. Mutable expiry and access tokens never enter content digests.

The private server port is `readBatch(actor,id,cursor)`, `stageBatch(actor,id,batch)`, `prepareBatch(actor,id)`, `commitPrepared(actor,id)`. Actor and verified session scope come from the server Auth port. Snapshot, restore and source-export issuance atomically bind that verified scope before returning an ID. Every new and legacy transfer-ID HTTP route requires it; old unbound capabilities must be recreated. Installation-wide quarantine status/release and publication reconciliation retain their independent fresh-admin authority. Paths and SQL table/object selectors are not transport inputs; resource ordinals resolve through the authorized immutable descriptor inventory, and logical records still pass the existing fixed managed-table/path/typed-record validators.

## Limits and replay

- Trusted Node↔control packets: decoded raw≤1MiB, encoded JSON≤2MiB,≤256 metadata parts or64 resource parts. Individual metadata retains its existing1000000B limit; physical members retain32MiB. Partial records bind exact size/hash/offset across packets. Nonfinal parts are at least24000B, bounding durable part counts.
- Renderer↔Rust↔Node stays64000B JSON/24000B raw. Only exact authenticated and snapshot-authorized recovery batch routes select the2MiB control parser. The fresh membership-only `/session` projection takes no payload fence, so it remains available during an atomic commit; all real transfer/resource actions retain their fences. Working status may use an exact-token context cache for at most30s and returns progress only; file/handle/save/new-operation authority is always freshly checked.
- One native-owned scheduler permits at most4 HTTP requests across its operations. Cursor lanes apply backpressure. Arrays/caches are bounded by packets/cohorts; records, receipts, body staging and validation progress live in SQL/private disk. Small body prefetch is at most one packet; an existing32MiB member can use private disk for incomplete parts.
- Metadata selects constrain the **ordinal interval before serialization/windowing**, then apply the byte budget. `LIMIT` after a broad range is insufficient: the initial full-volume attempt measured a fresh-statistics bitmap scan of868009 remaining rows/79031 buffers before returning256 rows,1.443s/page. Resource staging prefetches at most64 explicit ordinals and derives successors with indexed server-side MIN; missing positions fail.

Each write receipt binds a cursor and exact canonical packet digest. A lost response retries the identical packet. A completed receipt returns existing progress; a partially materialized resource packet resumes only its unacknowledged objects. Changed replay, gaps, descriptor/hash mismatch and excess bytes reject. Bulk inserts/counters acknowledge only persisted data; immutable conditional PUT replay verifies existing bytes. Owned destination keys are durably recorded before external IO, so cancellation can clean even a late PUT that never received a completion acknowledgement.

The runner owns transient retry: at most3 retries, with100/500/1500ms delays. Auth, validation, conflict, cancellation and expiry errors do not retry. The deterministic retry/concurrency fixture uses barriers/injected delays, without simulated network sleeps. User-facing progress/errors are Russian; raw SQL/provider errors, stacks, credentials and passphrases are not returned.

## Preparation and activation

`postgres-recovery-transfer.ts` owns transport receipts/claims/expiry/cleanup. `postgres-restore-preparation.ts` retains the existing typed Auth remaps, terminal-job handling, worker revocation, physical provenance, checkpoint/evidence checks and exact catalog rules. It reads at most256 records/1MiB of authenticated logical metadata, stops cooperatively between records after10s, performs existing bounded per-record body work outside SQL locks, and bulk-persists transformed rows/cursor under a fresh fenced claim. Existing typed availability, source manifest/site, producer-site and saved-evidence facts are fetched once per cohort in a short shared-fenced SQL transaction. At most256 fact objects and a separate1MiB output prefix are hydrated; large facts shorten the input prefix and resume durably. No fact cache survives the cohort, and state/body IO starts after the transaction ends.

Validation has durable phases for typed tables/constraints/reference closure, predecessor depth/cycles, fixed256-record inventory digest groups, catalog bundles and exact installed/pinned version availability. The inventory root is independently recomputed from acknowledged ordinal/size/SHA-256 proofs; the final aggregate has at most3907 fixed digests (≤250048B), never the installation's records. Immutable verified body digests also avoid repeatedly decoding identical validation PNGs. Checkpoint evidence uses the same pure projection over server-verified per-object path/size/MIME/SHA-256/SHA-1 proofs, reading state JSON once. Existing byte-backed producers compute their actual file digests and delegate to that identical projection. Legacy proofs without SHA-1/MIME pass a durable bounded upgrade with actual bytes/HEAD; manifest claims cannot supply missing proof.

Only READY can enter the final commit. It takes the existing installation exclusive fence FIRST, checks fresh admin/expiry/binding and an empty target, then uses setwise typed SQL INSERTs, ordered parents, pointers, sequences, provenance/quarantine and a durable report. There is no R2, filesystem, archive crypto or per-record preparation loop in that transaction. Lock wait is5s, statements≤15s, cumulative SQL105s; only the exact final-commit and existing snapshot-issuance client calls allow180s, below the configured240s Fluid function maximum. Unknown commit outcomes replay against the durable committed report.

Migration009 adds only private operational progress/receipt/part/proof/claim tables and indexes, revoked from public/anon/authenticated. They are excluded from `managedRecoveryTables`; portable logical schema8 remains correct. Migrations001–008 and the STORE/ZIP64/GCM/old-reader format are unchanged.

## Lifetime, shutdown and cleanup

Server snapshot/restore capabilities renew only while live and freshly authorized:60min sliding expiry, absolute24h from **current server capability creation**, independent of the archived header's age. Pin writes are coalesced: ordinary batches reuse live expiry while more than30min remains; actual renewal updates only unexpired matching pins. Expired capabilities/pins and claimed/deleted payloads never revive. Source pins release once all required bytes have been consumed.

The native operation holds access tokens only in memory. A replacement token is adopted only after the configured control verifies that exact bearer and returns the same actor/origin/mode/stable-session binding. User ID alone is insufficient. Opaque/no-session tokens remain exact-token bound and require a new authorized operation after refresh. Logout, new session, origin/mode change and role loss cancel admission, abort and drain owned requests. Disposal uses the original captured client to close its IDs before Auth is cleared. No active work/validated polling means no background database keepalive; finished handles retain30min lifetime.

Cancel marks a session terminal before bounded cleanup. Physical deletion waits for owned claims to drain/expire; keys and remaining work stay discoverable. Logical cleanup uses bounded SQL pages, physical cleanup uses at most64 keys at a time and cooperative time bounds. Existing worker maintenance/recovery admissions sweep expired work; no scheduler/service is added. Runtime close/root switch awaits already-running hourly maintenance and archive-owned work before persistence closes. The initiating restore is excluded only by a private object capability, never a renderer-supplied skip ID.
